# PRD: Workout Tracker v1.2 — Supabase Auth, данные пока локальные

## Для кого и какая задача

- **Для кого:** учебная демонстрация с настоящим входом в Supabase Auth и локальными
  тренировками.
- **Задача:** показать вход по email и паролю через Supabase, восстановление сессии,
  выход и разделение локальной истории по аккаунтам.
- **Важно:** это промежуточный этап. Вход настоящий, но тренировки ещё хранятся
  в `localStorage`, а не в Postgres. Серверная схема и RLS подготовлены, но store их
  пока не использует.

## Основной пользовательский сценарий

1. Открываешь приложение → пока восстанавливается сессия, видишь «Проверяем сессию...».
2. Если сессии нет — экран входа с email и паролем.
3. Входишь через Supabase Auth.
4. Видишь главную с 4 карточками упражнений и панель текущего пользователя.
5. Нажимаешь на карточку → вводишь подход: повторения, «есть доп. вес?» Да/Нет + вес.
6. Нажимаешь «Добавить подход» → заполняешь следующий.
7. «Сохранить тренировку» → запись сохраняется локально с UUID текущего пользователя.
8. Открываешь историю → видишь только свои тренировки в этом браузере.
9. Нажимаешь «Выйти» → Supabase очищает сессию, приложение возвращает на вход;
   тренировки остаются в браузере.
10. Входишь другим аккаунтом → у него своя локальная история.

## Экраны и элементы

### Экран 0 — Вход

Всегда содержит пояснение:

> **Вход через Supabase Auth**
>
> Email и пароль проверяются на сервере Supabase. Приложение не сохраняет пароль.
> Тренировки пока хранятся только в этом браузере.

Поля:

- Email;
- Пароль.

Кнопка «Войти». На время запроса — «Вход...», поля и кнопка заблокированы,
повторный клик невозможен. Защита от двойного клика — состояние плюс синхронный ref.

Ошибки показываются inline:

- «Введите email и пароль.»;
- «Неверный email или пароль.»;
- «Email не подтверждён. Подтвердите его по письму от Supabase.»;
- «Слишком много попыток входа. Подождите и попробуйте снова.»;
- «Вход по email отключён в настройках Supabase.»;
- «Нет связи с Supabase. Проверьте подключение.»;
- «Не удалось выполнить вход. Попробуйте ещё раз.».

Запрос входа ограничен 20 секундами; при таймауте кнопка снова становится активной.

Для несуществующего email и неверного пароля сообщение одинаковое. Сырой текст
ошибки Supabase в интерфейс не выводится.

Под формой явно указано:

> Вход по коду и через Google в этой версии отключены.
> Регистрация и восстановление пароля не входят в эту версию. Аккаунты создаются в Supabase.

Пароль не пишется в `localStorage`/`sessionStorage` и не логируется.

### Экран 1 — Главная

- Панель пользователя: имя (или часть email), email, кнопка «Выйти»
  (на всех внутренних экранах).
- Заголовок + кнопка «История».
- 4 карточки: Подтягивания / Отжимания / Брусья / Приседания.
- Блок «Последняя тренировка» — только записи текущего пользователя.
- Баннер старых записей без владельца: «Найдены старые тренировки без владельца: N».
  Перенос выполняется только после inline-подтверждения; «Оставить как есть» скрывает баннер.

### Экран 2 — Ввод подхода

Структура не изменилась: название упражнения, динамический список подходов,
«Добавить подход» / «Сохранить тренировку» / «Отмена». При сохранении запись получает
UUID текущего пользователя Supabase. Защита от двойного клика сохранена.

### Экран 3 — История

Список тренировок текущего пользователя, аккордеон, удаление. `store` не отдаёт чужие
записи и не удаляет их даже при прямом вызове из консоли. Это проверка UX, а не защита
от человека с доступом к браузеру.

### Выход

1. `supabase.auth.signOut()`;
2. очистка пользователя в контексте;
3. возврат на `/`;
4. экран входа с пустыми полями.

На время выхода кнопка показывает «Выход...» и заблокирована. Ошибка сети показывается
inline, пользователь остаётся в системе.

### Восстановление и смена сессии

- при загрузке — `getSession()` и состояние `restoring` без мигания экрана входа;
- `onAuthStateChange` обрабатывает `INITIAL_SESSION`, `SIGNED_IN`, `SIGNED_OUT`,
  `TOKEN_REFRESHED`, `USER_UPDATED`;
- истёкшая или отозванная сессия переводит приложение на экран входа;
- тренировки не зависят от сессии и не удаляются.

## Аккаунты

Аккаунты создаются в Supabase Dashboard → Authentication → Users.
В приложении нет регистрации, подтверждения email и восстановления пароля.

Пароли пользователей в коде, логах и документации не хранятся. Проверка пароля
выполняется Supabase Auth; приложение получает только пользователя и сессию.

## Хранение данных

| Ключ | Содержимое |
|---|---|
| `workout-tracker-data` | массив тренировок в `localStorage`; у новых есть UUID владельца |
| `sb-...-auth-token` | сессия Supabase; ключом и содержимым управляет SDK |
| `workout-tracker-session` | устаревший mock-ключ; приложением не читается |

Правила:

- приложение не читает и не пишет токены Supabase вручную;
- пароль не попадает в storage;
- `workout-tracker-session` не считается настоящей сессией и не пускает в приложение;
- старые записи без `userId` не удаляются автоматически и не показываются ни одному пользователю;
- перенос старых записей — явное одноразовое действие с подтверждением;
- после переноса владелец сохраняется, и запись больше не может быть присвоена другому;
- записи с mock-идентификаторами не переносятся автоматически;
- `results`, `approaches`, `reps`, `hasExtraWeight`, `extraWeightKg`, `date`, `time`, `id`
  при переносе не меняются;
- битый JSON трактуется как пустой список.

Подробная модель — в `data-model.md`.

### Ограничение безопасности

> **Вход настоящий, но данные пока локальные.**
> Supabase Auth проверяет пароль на сервере, а SDK хранит токены сессии. Приложение
> не хранит и не логирует пароль. При этом тренировки лежат в `localStorage`, а `userId`
> для локального store приходит с клиента. Проверки владельца в store — только UX.
> Для защиты данных нужен перенос тренировок в Supabase и работа RLS-политик из
> `supabase-workouts.sql`; до этого человек с доступом к браузеру или DevTools может
> читать и менять локальные записи.

## Технические решения

- **Vite 7 + React 19 + TypeScript 5.9** (strict)
- **React Router 7** — маршруты `/`, `/workout/:exerciseKey`, `/history`
- **Tailwind CSS 4 + shadcn/ui** (`base-nova` на `@base-ui/react`)
- **Auth-слой:** `src/auth/AuthContext.tsx`, `src/auth/user.ts`, `src/auth/errors.ts`
  (`signInWithPassword`, `getSession`, `onAuthStateChange`, `signOut`)
- **Клиент Supabase:** один экземпляр в `src/store/supabase.ts`; компоненты не импортируют
  `@supabase/supabase-js`
- **Store:** `src/store/index.ts`; операции тренировок пока синхронные и локальные
- **Сессия:** хранится и обновляется Supabase SDK, восстанавливается при загрузке
- **Сеть:** запросы Supabase ограничены 20 секундами; по таймауту показывается inline-ошибка
- **Ключи:** `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` из `.env.local`
- **Линтера и тестов нет**; проверки — `npm run build` и ручные/автоматизированные сценарии

## Проверки результата

Базовые:

1. **Сохранение:** после ввода 2–3 подходов тренировка появляется в истории с датой и всеми данными.
2. **Responsive:** на 375px карточки и формы читаются, кнопки нажимаются, горизонтального скролла нет.
3. **Персистентность:** после F5 данные и сессия сохраняются.

Вход и сессия:

4. Пустая форма показывает «Введите email и пароль.».
5. Неверные данные показывают «Неверный email или пароль.».
6. Во время запроса видно «Вход...», повторный клик невозможен.
7. Вход по коду и Google отсутствуют.
8. Успешный вход открывает Главную; F5 сохраняет сессию.
9. «Выйти» очищает сессию и возвращает на вход; тренировки остаются.
10. Пользователь A создаёт тренировку; B её не видит и не может удалить через store.
11. Возврат в A восстанавливает его локальную историю.
12. `workout-tracker-session` с mock-`userId` не пускает в приложение.
13. Перенос старых записей без `userId` выполняется только после подтверждения
    и только одному аккаунту.

Фактический прогон 2026-11-19: `npm run build` проходит; проверки остатков mock
и статических ключей пройдены. UI-сценарии проверены в headless Chrome с эмуляцией
ответов Supabase: пустая форма, неверные данные, состояние «Вход...», успешный вход,
восстановление сессии после F5, выход, сохранение локальных тренировок и 375px.
Отдельно проверено, что mock-ключ `workout-tracker-session` не пускает в приложение,
а пароль не попадает в `localStorage`. Успешный вход в реальный проект требует
тестового пользователя Supabase; пароль вводится только в браузере и в документации
не сохраняется.
