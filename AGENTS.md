# AGENTS.md — Workout Tracker

SPA-трекер тренировок: React 19 + TS + Vite, Tailwind 4 + shadcn/ui.
Вход: Supabase Auth (email + пароль и Google OAuth). Тренировки: `public.workouts` в Supabase Postgres,
доступ — только через асинхронный `src/store`. См. `decisions.md` и `supabase-workouts.sql`.
Запуск: `npm run dev` (порт 3000). Проверка: `npm run build`, `npm run test`.

## Инварианты
- Доступ к данным — только через `src/store`. Компоненты не трогают `localStorage`,
  не импортируют `@supabase/supabase-js` и не выполняют запросы к БД напрямую.
- Клиент Supabase создаётся в одном месте внутри `src/store`. Ключи — из env
  (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, образец — `workout-tracker/.env.example`);
  `service_role` в клиент не попадает. Auth-слой использует этот же клиент, второй
  `createClient` не создаётся.
- Вход — Supabase Auth: email и пароль (`signInWithPassword`) и Google OAuth
  (`signInWithOAuth`, провайдер настраивается в Supabase). Mock-аккаунты и вход
  по коду удалены; возвращать их без отдельного решения в `decisions.md`.
  Client ID и Client Secret Google живут только в настройках Supabase, не в коде и не в env.
- Пароли не хранятся в коде, документации и логах. Пароль живёт только в состоянии формы;
  сессию и токены хранит Supabase SDK, приложение их не логирует.
- `workout-tracker-session` — устаревший mock-ключ. Не читать его и не считать сессией;
  настоящая сессия — только Supabase Auth.
- Владелец строки — `auth.uid()` и RLS. `userId` / `user_id` с клиента не считается
  доверенным; проверки в UI и store — только UX, не защита.
- Тренировки читаются и пишутся в `public.workouts` через `src/store`. При ошибке
  Supabase store возвращает код ошибки, а не переключается на `localStorage`.
- Существующие записи в `workout-tracker-data` (`localStorage`) не удаляются, не читаются
  и не переносятся автоматически. Импорт старых данных — отдельная задача с явным
  подтверждением.
- `generateId()` — только из `@/utils/id`, копий не создавать.
- Импорты внутри `src` — через `@/...`.
- UI — только `src/components/ui/*` и токены `@theme`; хардкод цветов не добавлять.
- Без `window.alert` / `window.confirm` — inline-ошибки и состояние.
- Кнопки сохранения — с защитой от двойного клика. Асинхронные операции store показывают
  загрузку и inline-ошибку, повторный клик блокируется.
- Новая зависимость или смена стека — только после согласования, с записью в `decisions.md`.
  `@supabase/supabase-js` согласован 2026-11-19.
- Схема БД и политики меняются файлом `supabase-workouts.sql` и применяются в SQL Editor;
  расхождение кода и БД фиксируется в `data-model.md`.
- Тесты — Vitest в `workout-tracker/tests/**/*.test.ts(x)`. Чистые функции и store
  проверяются без сети; Supabase подменяется моками. `npm run test` сначала проверяет
  типы тестов через `tsconfig.test.json`, затем запускает Vitest. RLS юнит-тестами
  не доказывается — для неё остаются SQL и ручные сценарии.

## Готово, когда
`npm run build` и `npm run test` проходят, выполнены три проверки из `prd.md`
(сохранение → история, 375px, персистентность).

Для входа и серверного хранения дополнительно:
- вход по email и паролю, вход через Google, восстановление сессии после F5 и выход
  идут через Supabase;
- mock-ключ `workout-tracker-session` не пускает в приложение;
- пароли не попадают в код, логи и документы;
- пользователь видит, создаёт, меняет и удаляет только свои строки; `anon` получает отказ;
- вставка без `user_id` получает `auth.uid()`, подмена чужого `user_id` отклоняется;
- существующие записи в `workout-tracker-data` не тронуты и не импортированы.

## Коммиты
- Закончив задачу, агент сам делает коммит: не ждёт отдельной просьбы и не оставляет
  готовые изменения незакоммиченными.
- В коммит попадают только файлы задачи. Не коммитить `dist/`, `node_modules`,
  `test-results`, `.env` и любые секреты; перед коммитом смотреть `git status`
  и `git diff --staged`.
- Сообщение — короткое и по делу, в стиле истории: `fix(deploy): ...`, `add ...`,
  `fix ...`. Тело — только если нужно объяснить причину. Атрибуцию ассистента
  в сообщение не добавлять.
- Коммит делается после прохождения `npm run build` и `npm run test`. Если проверки
  падают — не коммитить, а сообщить о проблеме.
- Несколько несвязанных изменений — несколько коммитов, а не один общий.
