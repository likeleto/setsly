# План: настоящий вход Supabase Auth при локальных данных

Статус: реализовано 2026-11-19. Ветка `supabase`.
Стек не меняется: React 19 + TypeScript + Vite, Tailwind 4 + shadcn/ui.
Вход и сессия — Supabase Auth; тренировки пока хранятся в `localStorage` через `src/store`.

## Цель этапа

Заменить учебный mock-вход на настоящую проверку email и пароля в Supabase Auth.
Тренировки на этом этапе остаются локальными. Формулировка этапа:
**настоящий вход с ещё локальными данными**.

Что удалено:

- mock-аккаунты и пароли в исходниках (`src/auth/demoUsers.ts`);
- вход по коду;
- mock-диалог «Войти через Google» (`GoogleAccountDialog`);
- чтение mock-сессии из `workout-tracker-session`.

## 1. Последовательность экранов

```
Открытие приложения
      │
      ├── status = restoring
      │        └── «Проверяем сессию...»
      │
      ├── сессии нет / она истекла
      │        └── Экран входа (email + пароль)
      │
      └── сессия есть
               └── Главная (пользователь вошёл)
```

Пока сессия восстанавливается, экран входа не показывается — нет мигания формы
при перезагрузке.

## 2. Экран входа

Один экран, один способ входа: email и пароль.

**Заголовок**

> Workout Tracker

**Подзаголовок**

> Настоящий вход, данные пока локальные

**Пояснение**

> Вход через Supabase Auth
>
> Email и пароль проверяются на сервере Supabase. Приложение не сохраняет пароль.
> Тренировки пока хранятся только в этом браузере.

**Поля**

> Email
> Пароль

**Кнопка**

> Войти

**Состояния**

| Состояние | Что видно |
|---|---|
| `idle` | поля активны, кнопка «Войти» |
| `submitting` | поля и кнопка заблокированы, кнопка «Вход...», повторный клик невозможен |
| `error` | inline-сообщение под полями; email и пароль остаются заполненными |
| `success` | экран входа исчезает, открывается Главная |

Ошибки:

- пустой email или пароль → «Введите email и пароль.»;
- неверные данные → «Неверный email или пароль.»;
- email не подтверждён → «Email не подтверждён. Подтвердите его по письму от Supabase.»;
- слишком много попыток → «Слишком много попыток входа. Подождите и попробуйте снова.»;
- вход по email отключён в настройках Supabase → «Вход по email отключён в настройках Supabase.»;
- нет сети → «Нет связи с Supabase. Проверьте подключение.»;
- остальное → «Не удалось выполнить вход. Попробуйте ещё раз.».

Запрос входа ограничен 20 секундами: при таймауте показывается ошибка сети,
а кнопка снова становится активной.

Правила:

- сообщение для несуществующего email и неверного пароля одинаковое;
- сырой `error.message` от Supabase в UI не показывается;
- пароль хранится только в состоянии формы, не пишется в `localStorage`/`sessionStorage`
  и не логируется;
- форма использует `autoComplete="email"` и `autoComplete="current-password"`,
  чтобы работу с паролем мог взять на себя браузерный менеджер паролей.

**Отключённые способы**

Под формой явно написано:

> Вход по коду и через Google в этой версии отключены.
> Регистрация и восстановление пароля не входят в эту версию. Аккаунты создаются в Supabase.

## 3. Сессия

Провайдер `src/auth/AuthContext.tsx` использует единственный клиент из
`src/store/supabase.ts`; второй `createClient` не создаётся.

Состояние контекста:

```ts
type AuthStatus = 'restoring' | 'signedOut' | 'signedIn';

interface AuthApi {
  status: AuthStatus;
  user: AuthUser | null;
  signInWithPassword(email: string, password: string): Promise<AuthResult>;
  signOut(): Promise<AuthResult>;
}
```

### Восстановление

1. При старте `status = 'restoring'`.
2. Вызывается `supabase.auth.getSession()`.
3. Параллельно оформляется подписка `onAuthStateChange`.
4. Первое событие или ответ `getSession` переводит приложение в `signedIn` или `signedOut`.
5. Результат `getSession` не перетирает более свежее событие авторизации.

### Смена сессии

| Событие Supabase | Что делает приложение |
|---|---|
| `INITIAL_SESSION` | восстанавливает пользователя после загрузки / F5 |
| `SIGNED_IN` | обновляет пользователя, открывает Главную |
| `SIGNED_OUT` | очищает пользователя, показывает вход |
| `TOKEN_REFRESHED` | обновляет данные пользователя |
| `USER_UPDATED` | обновляет email/метаданные в панели |

Подписка снимается при размонтировании провайдера. В React StrictMode повторная
подписка безопасна.

### Вход

```ts
supabase.auth.signInWithPassword({ email, password })
```

После успеха пользователь сразу попадает в контекст, не дожидаясь события
`SIGNED_IN`. Пароль в контекст не передаётся и не сохраняется.

### Выход

```ts
supabase.auth.signOut()
```

- вызывается из панели пользователя;
- на время выхода кнопка показывает «Выход...» и блокируется;
- ошибка сети показывается inline, пользователь остаётся в системе;
- после успешного выхода сессия Supabase очищается, приложение показывает вход;
- тренировки в `workout-tracker-data` не удаляются.

### Где хранится сессия

Сессией управляет Supabase SDK. Токены доступа и обновления лежат в storage
браузера под ключом, которым управляет SDK (`sb-...-auth-token`), и не являются
паролем. Приложение эти значения не читает, не логирует и не пересылает вручную.

## 4. Пользователь и данные

`AuthUser` — представление пользователя Supabase в приложении:

| Поле | Источник |
|---|---|
| `id` | UUID из `auth.users` / сессии |
| `email` | `user.email` |
| `displayName` | `user_metadata.display_name` / `full_name` / `name`, иначе часть email до `@` |

Панель пользователя показывает имя и email, кнопка «Выйти» вызывает Supabase.

Тренировки пока локальные:

- `store.getAll`, `getLast`, `add`, `update`, `remove` работают с `localStorage`;
- новые записи получают UUID текущего пользователя;
- у каждого аккаунта своя локальная история в этом браузере;
- данные не синхронизируются между устройствами;
- RLS и `supabase-workouts.sql` подготовлены, но store ещё не обращается к таблице.

### Старые mock-записи

- `workout-tracker-session` больше не читается и не считается сессией;
- ключ не удаляется автоматически;
- записи с mock-идентификаторами не видны новым аккаунтам;
- автоматического переноса таких записей нет;
- записи без `userId` по-прежнему переносятся только явным подтверждением
  через `LegacyDataNotice` на текущий UUID-аккаунт.

## 6. Проверки

1. `npm run build` проходит.
2. Пустая форма показывает «Введите email и пароль.».
3. Неверные email/пароль показывают «Неверный email или пароль.».
4. Во время запроса видно «Вход...», поля и кнопка заблокированы.
5. Вход по коду и Google отсутствуют на экране.
6. Успешный вход открывает Главную; панель показывает email.
7. F5 восстанавливает сессию без мигания экрана входа.
8. «Выйти» очищает сессию Supabase и возвращает на вход.
9. Тренировки после выхода остаются в `localStorage`.
10. Второй аккаунт видит только свою локальную историю.
11. `workout-tracker-session` с mock-`userId` не пускает в приложение.
12. Регресс: сохранение тренировки, история, 375px.

Для успешного входа нужен тестовый пользователь Supabase. Пароль вводится только
в браузере; в документации и коде он не хранится.

## 7. Ограничения этапа

- Регистрации, подтверждения email из приложения и восстановления пароля нет.
- Пользователи создаются в Supabase Dashboard → Authentication → Users.
- Вход по коду и Google не реализованы.
- Тренировки локальные: очистка site data удаляет их; между устройствами синхронизации нет.
- `userId` для локального store по-прежнему приходит с клиента. Проверки владельца
  в store — только UX; серверная защита появится, когда тренировки переедут в Supabase
  и начнут работать RLS-политики из `supabase-workouts.sql`.
- Старые локальные записи с mock-идентификаторами не мигрируют автоматически.
